# 任务卡模板

填好以下正文，通过 `courier_send_message` 发送。尖括号是待填写项，示例不是实际路径或已发生的任务。正文最多 6000 个字符；完整合同可以放到双方已授权读取的文件中，但消息自身仍需包含关键动作、边界、队列和终态。

```text
任务 / 父目标 / 修订：<名称、版本；首次任务或接续哪一原消息 ID>
接收者 / 项目：<明确绑定别名、角色与项目>
目标 / 整体终态：<本次 owned 范围的全部必做结果；哪些仍由协调者负责>
工作目录 / 真实输入：<实际可访问路径、输入版本和接口；不猜造目录>
已接受成果 / 缺口：<应保留的有效产物与证据、尚未完成项>
第一实质动作：<一个真实可执行的检查、实现或命令及预期证据>
读写 / 唯一写权：<允许修改的文件或模块、保护路径、与其他 owner 的交接条件>
外传 / 工具 / 预算：<已有授权范围；禁止项；费用或资源上限>
完整职责队列：<实现 → 验证 → 常规修复与复验 → 集成/交接 → 已授权后继>
成功 / 失败 / 无新问题的后继：<每阶段的合法下一动作，或明确停止条件>
依赖 / 等待：<精确 owner、输入版本与接受条件、可独立工作、真实等待入口与超时动作>
交付物：<代码、测试、报告等实际产物位置和版本>
验收：<关键正例、反例、验证入口；协调者的独立检查>
回执：先用本会话 Hook 身份收件并 ACK。阶段完成不发 completed；完整完成 owned 职责后再 courier_return_result(completed)。无法继续则 courier_return_result(failed)，说明证据、有效成果、剩余职责与所需决定。
```

发送前检查：快速成功是否仍有后继？依赖晚到是否可以做独立工作？后继未授权时是否有明确停止分支？所有职责提前完成时是否可以正确收口？原任务仍活跃时，接续卡是否会产生重复写权？
